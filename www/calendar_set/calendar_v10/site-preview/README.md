# 연습실 홈페이지 구조 미리보기

기존 Cafe24 계정에 별도 경로 `/calendar_set/calendar_v10/site-preview/`로 공개한다. 로그인은 추가하지 않는다. 운영 홈·메뉴·사이트맵에서 연결하지 않고 문서와 HTTP 응답에 `noindex,nofollow,noarchive`를 설정한다. 주소를 알고 있으면 접속할 수 있다.

## 구조와 데이터 소유

기존 구현은 **일부 있음**이다. 기존 v10 안내 자료·요금표·사진·달력·공개 예약 캐시와 로컬 `server.py`를 재사용한다. 빠진 부분인 독립 주소의 소개·공간·요금·위치·이용 안내만 이 디렉터리에서 소유한다.

- `build.py`: 기존 `home_infopage/homepage-section_mobile.html` 요금, `popup_info.html` 크기를 읽어 정적 HTML 12개를 생성한다. 사진은 원래 경로를 참조한다.
- `calendar-v11/`: v10에서 명시적으로 복사한 독립 UI 버전이다. HTML·자체 런타임·캐시 조회 JS·SwipeCalendar·CSS·브라우저 가드를 별도로 소유한다. `build.py`는 이 버전을 다시 복사하거나 덮어쓰지 않는다. 변경 가능성이 없는 FullCalendar 라이브러리와 로고 이미지만 원래 경로를 공유한다.
- 예약 링크는 `booking_links()`가 상단의 예약하기 메뉴로 여는 `/schedule/` 페이지에서만 제공한다. 공통 메뉴와 겹치는 본문 이동 카드·상세 페이지 이동 버튼·하단 CTA는 제거했다. 예약 방법·예약정보 확인·새벽 대관 문자 문의도 이 페이지에 모았다. 일정표 안의 네이버·스페이스클라우드·가격표 버튼과 안내 팝업/메뉴는 제거했다. 원래 캘린더로 나가는 링크도 제거했다.
- 예약 조회 경로: 미리보기 `/schedule/` → `calendar-v11/index.html` → 복사한 `calendar-v11/server-calendar-sync.js` → 기존 `/calendar_set/calendar_v10/data/events.json`. 운영 DB 원장에서 생성된 공개 캐시를 조회하며 새 DB·스키마·작업 큐·캐시 소유자는 없다.
- 기존 보호 목적은 DB 원장을 기준으로 한 공개 캐시 조회와 예약 변경 경로의 분리다. 동일한 조회 경로를 유지하며 예약 생성·취소·SMS를 실행하지 않는다.
- 소개 페이지의 생성 파일은 직접 편집하지 않고 `build.py`에서 재생성한다. `calendar-v11/`은 독립 소스이므로 직접 편집한다. `style.css`와 `site.js`가 새 소개 UI를 담당한다. 비드래그 이미지·링크의 기본 드래그는 막는다.

## 빌드와 로컬 실행

```sh
python3 www/calendar_set/calendar_v10/site-preview/build.py
python3 www/calendar_set/calendar_v10/site-preview/serve.py
```

로컬 주소는 `http://localhost:5088/`. 서버는 기존 정적 파일 핸들러를 재사용한다. 로컬에서는 로컬 `data/events.json`을 읽고 Cafe24에서는 운영 공개 캐시를 읽는다. 실제 데이터 확인 기준은 배포 주소다.

## 배포·복구 경계

작업 디렉터리만 커밋·푸시한 뒤 canonical target 설정 `ops/cafe24-production-target.env`의 호스트·APP_ROOT를 검증한다. 그 아래 `calendar_set/calendar_v10/site-preview/`에 HTML·CSS·JS·`.htaccess`만 전송한다. 전체 `deploy-cafe24.sh`는 전체 복구 및 서비스 변경까지 실행하므로 이 정적 미리보기 배포에는 사용하지 않는다. Python·README·로컬 캐시는 업로드하지 않는다.

미리보기 경로 안에서만 배포하며 기존 홈·Apache 전역 설정·서비스·예약 캐시는 변경하지 않는다. 롤백은 이 디렉터리를 웹 루트 밖으로 이동하면 된다. DB 마이그레이션은 없다.

## 검증 범위

12개 독립 페이지와 정적 참조의 HTTP 성공, 페이지별 고유 제목·H1·검색 제외, PC/모바일 폭, 이미지 드래그 방지, 실제 달력 표시 및 룸 필터를 확인한다. 배포 전후 운영 홈 HTML과 원래 캐시 로더의 해시가 같아야 한다. 데이터 조회만 연결하므로 실제 예약·취소·문자 발송 회귀 동작은 실행하지 않는다.

- 증상 → 판정 → 부작용 → 결과: 사이트의 기존 캘린더 링크와 iframe 내 예약 버튼이 중복 노출됨 → 부모 소개 UI와 캘린더 UI의 책임이 섞여 있음 → 예약 채널 이동을 부모 페이지로 이동 → 일정 조회는 동일한 운영 공개 캐시, 예약은 기존 외부 채널로 연결.
- 기존 구현은 **일부 있음**: 기존 버튼 URL, 룸 선택·주/월 전환·공개 캐시를 재사용한다. 원본을 언제든 사용할 수 있게 보존하라는 요청에 따라 UI 파일만 별도 버전으로 복사했다. 중복 예약 처리·DB·작업 큐는 만들지 않았다.
- 원본의 비편집 예약 조회, 캐시 타임아웃, 요청 합치기, 범위 필터, 60초 갱신을 보존한다. 별도 데이터 수집이나 외부 예약 쓰기는 추가하지 않는다.
- 변경 검증은 두 외부 예약 링크, iframe 내부 예약 링크 부재, PC/모바일 및 룸·주/월·날짜 선택, 로더 실패 후 재조회, 원본 파일 해시 보존에 한정한다. 외부 예약 생성·취소·결제는 변경하지 않았으므로 실행하지 않는다.
- 로컬 검증 결과: PC 1440px / 모바일 390px 가로 넘침 없음. 예약 버튼 2개가 부모에 있고 iframe의 링크는 0개다. B홀 선택, 주/월 전환과 일정 렌더링이 정상이다. 복사한 로더의 실패 후 재조회·동시 요청 합치기·조회 범위 필터를 확인했으며 원본 6개 파일 해시는 복사 전후 일치한다.


## 예약 메뉴로 통합

기존 구현은 **일부 있음**: `shell()`의 공통 메뉴, `/schedule/`의 독립 일정표와 `booking_links()`를 재사용한다. 예약 접근을 돕기 위해 본문·하단에 반복했던 이동 요소가 메뉴와 중복된 것이 이번 정리 대상이다. 예약 링크는 예약하기 페이지 한 곳에서만 제공하며 새 경로나 예약 처리 기능은 만들지 않는다. 공간 사진·상세 정보·요금·위치·이용 규정은 유지한다.

검증은 전체 페이지의 예약 링크 위치, 공통 메뉴 접근, 공간 상세 링크, PC/모바일 배치, 예약 페이지의 일정표 표시로 한정한다. v10 원본과 v11 캘린더 로직·DB·외부 예약 처리는 변경하지 않아 해당 기능의 반복 회귀시험이나 실제 예약 실행은 제외한다.

## 메뉴 고정·스와이프·사진 준비

- 증상 → 판정 → 실행 → 외부 결과: 페이지 전체를 드래그해 이동하면 헤더도 함께 이동하고,
  인접 HTML만 준비한 뒤 다시 `location.assign()`하여 사진이 재다운로드됐다.
  원본 사진 HTTP 응답의 `no-store`도 확인했다. 기존 `shell()` 메뉴와 `site.js`의
  프리페치/제스처를 재사용하며, 빠진 이미지 준비와 화면 재사용만 같은 소유 위치에 연결했다.
- 기존 구현 **일부 있음**. `shell()`의 헤더를 이동 본문 밖의 sticky 영역으로 옮겼다.
  메뉴 순서와 `aria-current`가 경로 기준이며 별도 라우트 목록을 추가하지 않았다.
  정적 HTML의 본문을 최대 8개까지 탭 메모리에 보관하고 첫 사진 2장을 미리 decode한다.
  화면 전환은 같은 DOM/사진을 이어 사용한다. 느린 사진은 최대 1.2초만 기다리고,
  HTML 조회 실패는 기존 URL 이동으로 복구한다. 절약 모드에서는 추측 다운로드를 하지 않는다.
- 제목·메뉴 활성 표시·뒤로/앞으로·스크롤 위치를 연결했다. 연속 요청은 마지막 요청만 적용한다.
  세로 스크롤·확대·가장자리·입력 요소·캘린더 제스처·새 탭 열기·동작 줄이기를 보존한다.
  사진/링크의 기본 드래그 방지도 유지한다.
- 준비 화면에서는 iframe을 로딩하지 않는다. 예약 페이지가 실제로 열릴 때만 기존 공개 캐시
  캘린더를 실행하며 떠날 때 iframe과 룸 선택 대기 타이머를 정리한다. 다시 들어오면 새로 조회한다.
  영구 캐시, 서비스 워커, 예약 데이터 캐시 소유자, DB/스키마/큐는 추가하지 않았다.
- `ops/site_preview_swipe_selftest.cjs` 기존 검사를 확장하여 54개 경계를 확인했다.
  전체 메뉴 양방향·룸 상세·취소·천천히 넘기기·재시도·오프라인 복구·사진 사전 준비/재사용·
  연속 이동·뒤로가기 위치·절약 모드·보조키 클릭을 포함한다.

### 스와이프 전체 재검토

표 전용 예외는 추가하지 않았다. 기존 가로 스크롤 보호와 세로 스크롤 보호를 다시 확인했고,
전체 화면의 `touch-action`이 기본값인 점, 높이만 달라져도 `resize`가 제스처를 초기화하는 점을 수정했다.
`pan-y pinch-zoom`으로 브라우저의 세로 스크롤/확대와 앱의 가로 입력을 구분하며,
포인터 캡처로 터치·펜·마우스가 표/사진/링크 경계를 지나도 같은 제스처를 추적한다.
초기 작은 대각선 흔들림은 바로 세로로 판정하지 않고, 실제 방향이 드러날 때까지 기다린다.
높이 변화는 진행 중 동작을 유지하고, 가로 폭 변화·멀티터치·취소는 복귀시킨다.
구형 Touch Events도 같은 `begin/move/finish`를 사용한다.
설계 참고: [MDN touch-action](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/touch-action),
[Pointer capture](https://developer.mozilla.org/en-US/docs/Web/API/Element/setPointerCapture).
추가 검사는 세 입력 종류, 주소창 높이 변화, 초기 대각선, 멀티터치/취소/세로 스크롤이다.
브라우저에서 요금표 셀, 사진, 일반 본문을 시작점으로 실제 드래그 양방향/연속 이동을 확인했다.
모바일 폭 검증은 브라우저 화면 크기 에뮬레이션이며 물리 휴대폰 조작을 대체했다고 주장하지 않는다.
